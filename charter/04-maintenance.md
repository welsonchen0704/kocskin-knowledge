# 04 維護協議：未來的弱模型怎麼安全地更新本包
版本：2026-07-03

## 1. 權限分級（動之前先對照）

**可自行改（改完 read-back，並在 lessons.md 記一筆「制度變更」）**
- lessons.md：追加教訓（唯一鼓勵頻繁寫的檔）
- 01-dispatch.md 第 0 節：環境驗證結果（模型清單、版本、日期）
- ref/ 內的「事實過期修正」：僅限有 V2 或官方來源佐證的更新（附來源）
- 路由表新增一列（新 skill / 新 DB 上線時）
- 錯字、失效路徑、失效 URL 的修正（修正前先確認新值真的有效）

**先問 Welson 才能改（提出 diff 供他核准，不可先改再報）**
- CLAUDE.md 第 1 節硬紅線：任何增刪改
- compliance-rules.md：任何實質規則變動（新增禁語除外——從嚴方向可自行加，
  從寬方向一律先問）
- 04（本檔）的權限分級本身
- 刪除任何規則或檔案
- FB Ads 寫入協議（R4）的任何字

**絕對不做**
- 為了讓某個任務過關而臨時放寬規則（正確做法：任務停下，問人）
- 在多處複寫同一規則（正確做法：一處為源，他處引用）

## 2. 踩坑後的教訓寫回（當個 session 內完成，不留到下次）
寫進 lessons.md，格式固定：
```
### L-〔流水號〕｜〔YYYY-MM-DD〕｜〔一句話標題〕
情境：發生了什麼（含觸發任務）
錯誤：具體錯在哪（引用錯的輸出/數值）
規則：以後怎麼做（一句可執行的指令句）
落點：這條規則是否需要升級進正式檔？〔留在lessons／建議進CLAUDE.md-R?／建議進ref/xx〕
```
判斷落點：同類教訓出現第 2 次 → 提議升級進對應正式檔（走權限分級）。
一次性的環境怪癖留在 lessons 即可。

## 3. 精簡觸發條件（防止規則堆積成無人讀的長卷）
任一成立 → 在回覆末尾向 Welson 提議做一次精簡（列出候刪/候併項，等他核准）：
- CLAUDE.md 超過 120 行
- lessons.md 超過 25 條
- 同一主題的規則出現在 3 個以上位置
- 距上次精簡超過 90 天
精簡原則：合併同類、刪已被結構取代的提醒（例：協議已內建 read-back，
就刪「記得檢查」類軟提醒）、過期事實直接刪不留屍體。精簡前整檔備份到 backup/
（檔名附日期）。

## 4. 同步義務（單一來源的維護面）
- 合規規則：源 = ref/compliance-rules.md → 改後同步 kocskin-compliance-check skill。
- 品牌貼文規格：源 = ref/brand-and-content.md → 改後同步 kocskin-post-writer skill。
- claude.ai userPreferences 與 Claude Code 專案的 CLAUDE.md 應為同一版；
  改任一份時提醒 Welson 更新另一份（AI 無法自行改 userPreferences）。
- 商品事實永遠不進本包，只在 V2。「商品事實」定義＝成分、售價、規格、宣稱內容、
  庫存狀態等會變動的 SKU 資料。**兩類例外允許存在本包**（皆須標註「以 V2 為準」）：
  (a) 戰略角色清單（ref/brand-and-content.md 四星系）；
  (b) 已釀過事故的防呆紅線（如紅麴納豆每日 1 顆、停售品清單）。
  例外以外的 SKU 事實出現在本包 → 視為 bug，改為指向 V2 的引用。

## 5. 版本標記
每個檔案頭部保留「版本：日期」；改動時更新日期並在 lessons.md 記變更一行。
不做複雜版本號，日期即版本。
