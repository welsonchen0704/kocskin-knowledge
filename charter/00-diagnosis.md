# 00 診斷報告：目前 harness 前三大問題與修法
版本：2026-07-03（Fable 5 制度重整 session 產出）
用途：本包所有檔案的立論依據。維護時若刪改本檔結論，需同步檢查引用它的檔案。

## 觀測範圍與極限（誠實標註）
本診斷基於：claude.ai 記憶內容、userPreferences 中的 claude.md（2026-06-28 版）、
本環境可見的 5 個 user skills、MCP 工具清單（Notion / Facebook Ads / Gmail /
Google Calendar / Google Drive / Canva / HyperFrames）。
**看不到的**：Welson 的 Claude Code 專案實際檔案、subagent 定義、歷史對話原文。
以下「症狀」有兩種標記：〔實證〕= 記憶中有明確事故紀錄；〔結構推斷〕= 從現有
檔案結構必然導出的風險，尚無事故但遲早發生。

---

## 問題一：事實與規則混寫在每次都載入的檔案裡 → token 漏 + 資料過期最危險

**症狀**
- claude.md 內含商品層級事實（紅麴納豆每日 1 顆、SKU 改名對照、四星系商品清單、
  字數規格），但同一份檔案又宣告「V2 是唯一權威」。〔結構推斷〕兩處遲早不同步，
  弱模型會拿 claude.md 的過期事實直接寫，因為它「就在眼前」而 V2 要查。
- 記憶裡存了大量會過期的營運數字（Q1 ROAS 7.72x、NT$566K 花費、M1 回購 7.4%）。
  弱模型傾向把「記憶裡的數字」當「現在的數字」用進決策。〔實證〕KOCSKIN 業務
  高度季節性（9+11 月佔全年淨利 70.8%），拿 Q1 基準推全年必然失準。
- 曾發生幣別單位事故（預算寫成分為單位）。〔實證〕已有補救協議，但協議散在記憶裡，
  不在單一可指認的檔案位置。

**修法（已落實在本包）**
1. CLAUDE.md 只留三類內容：硬紅線（違反即重大損失）、路由表（什麼任務讀什麼檔）、
   工作模式開關。商品事實一律指向 V2，claude.md 不再複寫任何 SKU 層級數字。
2. 新增「數字保鮮規則」寫入 CLAUDE.md：任何用於決策的營運數字，必須標註來源與
   日期；超過 14 天的數字用於預算/投放決策前，必須先用 MCP 重查。記憶裡的數字
   一律視為「歷史背景」不是「現值」。
3. FB Ads 寫入協議收斂成單一 checklist，放進 CLAUDE.md 硬規則區（見該檔 R4）。

## 問題二：驗證靠「同一個腦自己說做完了」→ 最容易出錯

**症狀**
- 合規審查 skill 存在，但觸發靠模型「記得要跑」。弱模型在長對話後段最容易跳過。
  〔結構推斷〕今年已踩過美白文號的雷（claude.md 自述），代表守門曾經失效過一次。
- 產出→自我宣告完成→交付，中間沒有 read-back、沒有 fresh-context 覆核。
  〔實證〕預算幣別事故本質就是「寫入後沒有讀回驗證」。
- Notion 寫入（/結束流程）有預覽確認，但寫完後「實際寫入 vs 宣稱寫入」沒有強制比對。

**修法（已落實在本包）**
1. 「驗證不自驗」入憲：見 01-dispatch.md 第 5 節。檔案改動用 read-back、
   對外文案用合規關卡（在 Claude Code 用 fresh subagent；在 claude.ai 無 subagent
   時用「分離訊息重審」替代——先產出、下一輪只做審查不做修改）。
2. 合規審查從「建議」升為「管道順序」：任何對外內容的產出鏈固定為
   查V2合規卡 → 產出 → 合規審查 → 交付，順序不可為了省時間重排。寫入 CLAUDE.md。
3. 高風險寫入（預算、Notion 正式寫入、發布）一律「寫後讀回、逐欄比對、回報差異」。

## 問題三：單人樞紐 + 基礎設施無 runbook → 一次中斷就斷鏈

**症狀**
- 整套技術棧（5 個 Railway 服務、2 個 Cloudflare Worker proxy、AI Studio、
  GA4/Meta 整合）只有 Welson 一人掌握，且部署是手動 `railway up`。〔實證〕
  復康巴士 bot 有已知未修 bug（週六日期檢查誤通過）。
- AI session 之間的交接靠記憶系統自動摘要，沒有人工可控的「狀態快照」規範
  ——其實有（狀態快照紀錄 DB），但只在 /結束 時觸發，session 中途斷線就丟失。
- token 漏最大處：〔結構推斷〕主對話直接執行大量讀取（掃 Notion 多頁、讀長報表）
  而不是派出去，導致長 session 後段 context 被原始資料塞滿、規則被擠出注意力
  ——這正是合規跳關最常發生的時點。

**修法（已落實在本包）**
1. 「指揮官不下場」入憲（01-dispatch.md）：大量讀取/掃描/批次改檔派 subagent，
   主對話只收結論。claude.ai 環境無 subagent 時的替代：把大量讀取切成獨立對話，
   結論寫進 Notion 再開決策對話。
2. 維護協議（04-maintenance.md）規定：每次踩坑，教訓必須在當個 session 寫回
   lessons.md，不靠記憶系統自動吸收。
3. 給未來 session 的信（05-letter.md）列出 runbook 缺口清單，建議 Welson 排程補齊
   （這超出 AI 能自主完成的範圍，需要他提供憑證與部署權限資訊的存放決策）。

## 三個問題的共同根因
規則的「存在」和規則的「在執行時被看見且被強制」是兩回事。
現行 harness 規則齊全但強制力靠模型自覺；本包的所有設計都在把「自覺」換成
「結構」：順序不可重排的管道、寫後必讀回、驗收換人做、事實只有一個家。
