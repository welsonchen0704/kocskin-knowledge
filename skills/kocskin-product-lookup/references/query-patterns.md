# 查詢模式範本（Search + Fetch 驗證 pattern）

**Data Source ID**：`16d640a9-9f0b-441f-a670-821c6b4189ac`
**Collection URL**：`collection://16d640a9-9f0b-441f-a670-821c6b4189ac`

統一流程：`notion-search`（多組關鍵字擴召回）→ `notion-fetch`（對候選驗證屬性）→ 過濾。

> **2026-07-11 更新**：`notion-query-data-sources`（SQL 全表查詢）實測可用——多條件、清單、全庫查詢**優先下 SQL**，本檔的 search+fetch 模式保留給「語意模糊、只記得片段關鍵字」的查詢當兜底。舊的 `mcp__notion__API-query-data-source` 仍是壞的，勿用。`notion-search` 是 semantic search，單一關鍵字可能漏召回，所以下列每個模式都列「建議關鍵字組」。

## 模式 1：單品查詢

**情境**：「玫瑰精華的成分是什麼」「3D 面膜有哪些成分」「超能量眼霜多少錢」

### Step A：search

```
notion-search(
  query: "<產品名稱片段>",
  data_source_url: "collection://16d640a9-9f0b-441f-a670-821c6b4189ac",
  page_size: 10,
  filters: {}
)
```

### Step B：fetch + 驗證

對 top 3 結果的 page id 分別 `notion-fetch`。驗證：
- `SKU狀態 == "在售"`（若多筆同名，優先在售）
- `產品名稱` 與使用者問的關鍵字吻合度

若找不到，改搜尋「系列名 + 品類」（例如「玫瑰 眼霜」）。

---

## 模式 2：系列 / 分類清單

**情境**：「玫瑰抗老系列有哪些」「3D 全能系列有哪些在售商品」

### Step A：search（多組關鍵字）

系列名關鍵字可能召回不全（因為 search 看的是頁面內容，不是 select tag），所以用下方〈附錄：各系列關鍵字建議表〉挑 2-3 組。舉例：

```
# 玫瑰抗老系列
notion-search(query: "玫瑰超導", ...)
notion-search(query: "山茶花外泌體", ...)
notion-search(query: "玫瑰 抗老", ...)
```

把三次結果的 page id 聯集（去重）。

### Step B：fetch + 驗證

對每個候選 `notion-fetch`，驗證：
- `系列分類 == "<目標系列名>"`（例如 `"玫瑰抗老系列"`）
- `SKU狀態 == "在售"`

驗證通過的才進入輸出。

---

## 模式 3：膚質 / 需求篩選

**情境**：「敏感肌可以用的商品」「乾性肌保濕商品」「抗老商品」

### Step A：search

```
# 敏感肌
notion-search(query: "敏感肌", ...)
notion-search(query: "敏肌修護", ...)
notion-search(query: "低敏 修護", ...)

# 乾性肌 + 保濕
notion-search(query: "乾燥 修護", ...)
notion-search(query: "玻尿酸 保濕", ...)
notion-search(query: "保濕 乾性", ...)
```

### Step B：fetch + 驗證

驗證：
- `適用膚質 contains "敏感肌"` OR `"全膚質"`（全膚質也算敏感肌可用）
- `SKU狀態 == "在售"`
- 若使用者指定了其他條件（例如「主力商品」），加驗 `商品定位角色 == "主力商品"`

---

## 模式 4：定位 / 價格篩選

**情境**：「主力商品有哪些」「1500 元以下的引流商品」「回購商品清單」

### Step A：search

定位類型無法直接用 select tag 搜，需用相關詞：

```
# 引流商品（通常是低價、吸客的入門款）
notion-search(query: "引流 洗面乳 洗面皂", ...)
notion-search(query: "體驗 入門", ...)

# 主力商品
notion-search(query: "主力 代表", ...)

# 回購商品（消耗型）
notion-search(query: "週期 補充 回購", ...)
```

若關鍵字找不到，**兜底策略**：改為「分類清單」查詢（模式 2），先拿到全系列，再用 fetch 驗證 `商品定位角色` 過濾。

### Step B：fetch + 驗證

驗證：
- `商品定位角色 == "<目標定位>"`
- `SKU狀態 == "在售"`
- 價格條件：`售價 <= <上限>` 且/或 `售價 >= <下限>`

---

## 模式 5：商品比較

**情境**：「A 和 B 的差異」「H7 精華和加大版差在哪」

### Step A：search（找到兩支）

若已知產品名，直接用模式 1 定位兩支的 page id。

### Step B：fetch 兩支

兩次 `notion-fetch`，取得完整 properties。

### Step C：整理比較表

並列比較「售價、容量、核心成分、適用膚質、主打賣點、商品定位角色、系列分類」。相同欄位合併說明，差異欄位獨立列出。

---

## 模式 6：組合推薦

**情境**：「乾性肌 1500 元預算的保養組合」「敏感肌三件組」

### Step A：用模式 3 拿候選

先執行「膚質篩選」取得候選商品清單。

### Step B：fetch + 組合邏輯

在候選中挑：
- 清潔 1 支（`產品系列 == "清潔"` 或 `系列分類 == "基礎清潔系列"`）
- 化妝水 / 精華 / 乳液 1-2 支（`產品系列` 為「保濕 / 抗老 / 美白淡斑」）
- 面膜或特別護理 1 支（選配，若預算允許）

合計金額盡量接近預算上限（不超過）。

### Step C：輸出推薦理由

- 為什麼選這組（扣回核心購買動機與膚質匹配）
- 合計金額
- 使用順序（清潔 → 化妝水 → 精華 → 乳液 → 面膜週 2-3 次）

## 模式 7：停售商品查詢（只在使用者明確要求時）

**情境**：「停售的商品有哪些」「以前的氣墊粉餅補充蕊還有嗎」

**現況**：V2 **已有停售列**（2026-07-13／14 起），一律用 SQL 即時查，不引用快照。紅線品「氣墊粉餅補充蕊」「益生守護者 7 日體驗包」為未開發未販售、不在 V2（補充蕊在「Kocskin 商品成本表」DB）。

### 處理方式

1. 先用 SQL `WHERE "SKU狀態" = '停售'` 確認即時狀態。
2. 輸出時每筆標示 **[已停售]**，並加一句：「此商品已停售，對外行銷素材請勿提及。」「暫時停賣」特例（如 KOCS001）與完整紅線敘述以 `kocskin-compliance-check/references/brand-rules.md`〈一、停售商品〉為正本。
3. 「氣墊粉餅補充蕊」「益生守護者 7 日體驗包」查不到是正常的——照實說明「未販售」，並提醒對外素材不得提及。

## 除錯心法

若 search 結果和預期差異很大：

1. **召回過多**：搜到太多不相關商品 → fetch 前幾筆看 `系列分類` / `產品系列`，找出共通特徵詞加入下次 query
2. **召回過少**：只搜到 1-2 筆 → 用〈附錄〉換關鍵字再搜，或改用更廣的詞（例如「玫瑰抗老」→ 「玫瑰」）
3. **完全沒召回**：檢查 `data_source_url` 是否為 `collection://16d640a9-9f0b-441f-a670-821c6b4189ac`
